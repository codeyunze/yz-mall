# yz-mall 日志系统设计方案

> 状态：设计稿（保留现有 Logstash TCP + SkyWalking GRPC 策略，按阶段演进至 Kafka 总线 + SigNoz）  
> 适用范围：`mall-gateway` / `mall-sys` / `mall-pms` / `mall-oms` / `mall-auth` 等业务服务  
> 更新日期：2026-07-26

---

## 1. 背景与目标

### 1.1 现状痛点

| 现状 | 问题 |
|---|---|
| 应用同时挂 `LogstashTcpSocketAppender` + `GRPCLogClientAppender` | 双通道序列化与出网；任一端不可用产生周期性 WARN |
| 检索在 ES/Kibana，链路在 SkyWalking | 两套体系，TraceId 可互查但运维成本高 |
| 计划用 **SigNoz** 替换 SkyWalking | 若继续「应用直连多后端」，接入点会继续膨胀 |
| 缺少统一的 HTTP 出入站审计日志 | 排障、对账、安全审计依赖零散业务日志 |

### 1.2 设计目标

1. **应用侧只打一次远程日志**（优先 Kafka），下游多消费者订阅，互不影响。  
2. **三类日志统一建模**：运行日志、入站 API 访问日志、出站外部调用日志。  
3. 入站/出站日志必须可还原排障上下文：**query、body、header、cookie**（含脱敏策略）。  
4. **平滑演进**：现阶段保留现有上传策略；Kafka / SigNoz 按阶段上线，可回滚。  
5. 与现有基建对齐：已有 Kafka（`192.168.3.237:9094`）、ES/Logstash、后续 SigNoz + OpenTelemetry Collector。

### 1.3 非目标（本期不做）

- 不在本期替换全量业务埋点为 OpenTelemetry Metrics。  
- 不把业务 MQ 消息体默认全量落日志（与 HTTP 审计日志分离）。  
- 不要求 ClickHouse/ES 双写业务库数据；日志存储与业务库解耦。

## 2. 总体架构

### 2.1 目标拓扑（Kafka 为日志总线）

```text
┌──────────────────────────────────────────────────────────────────────────┐
│                         应用进程（各微服务）                              │
│  console / 本地文件（排障兜底）                                           │
│  ┌─────────────┐  ┌──────────────────┐  ┌────────────────────────────┐  │
│  │ Runtime Log │  │ Inbound Access   │  │ Outbound HTTP Call Log     │  │
│  │ (logback)   │  │ (网关/Filter)    │  │ (Feign/RestClient 拦截器)  │  │
│  └──────┬──────┘  └────────┬─────────┘  └─────────────┬──────────────┘  │
│         │                  │                          │                 │
│         └──────────────────┼──────────────────────────┘                 │
│                            ▼                                            │
│                   KafkaAppender（异步）                                  │
│                   统一 JSON Envelope                                    │
└────────────────────────────┬─────────────────────────────────────────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  Kafka Cluster  │
                    │  （日志专用 Topic）│
                    └────────┬────────┘
           ┌─────────────────┼─────────────────┐
           ▼                 ▼                 ▼
   ┌───────────────┐ ┌───────────────┐ ┌────────────────────┐
   │ Logstash      │ │ OTel Collector│ │ （可选）归档/数仓    │
   │ → Elasticsearch│ │ → SigNoz      │ │ S3/OSS / Cold ES   │
   │ Kibana 检索   │ │ Trace+Log UI  │ │                    │
   └───────────────┘ └───────────────┘ └────────────────────┘
```

**原则：生产者与消费者解耦。** 新增「再接一个分析系统」= 加一个 Consumer Group，不改应用。

### 2.2 过渡期拓扑（保留现状）

```text
应用
 ├─ console / file          （保留）
 ├─ Logstash TCP :4560      （保留，阶段 0～2）
 ├─ SkyWalking GRPC Log     （保留至 SigNoz 切换完成）
 └─ KafkaAppender           （阶段 1 起并行双写，验证后切主）
```

双写窗口内以 Kafka 为准做对账；确认消费与检索稳定后，再下线 TCP / GRPC。

### 2.3 为何选 Kafka 而不是继续直连

| 维度 | 直连多 Appender | Kafka 总线 |
|---|---|---|
| 应用复杂度 | 每加一个后端加一个 appender | 应用只认 Kafka |
| 后端故障隔离 | Logstash 挂 → 应用刷 WARN | 缓冲在 Broker，应用侧影响小 |
| 多系统接入 | 难 | 新 Consumer 即可（ES / SigNoz / 审计仓） |
| 峰值削峰 | 弱 | 强 |
| 与大厂实践 | 小团队常见 | 互联网标配（日志 / 链路 / 审计分流） |

## 3. 日志分类与 Topic 设计

### 3.1 三类日志

| 类型 | `log_type` | 用途 | 采集点 |
|---|---|---|---|
| 运行日志 | `app` | 业务/框架运行输出 | logback root / 业务 logger |
| 入站访问 | `http_in` | 外部 → 本系统 API | **优先网关**；服务内 Filter 兜底 |
| 出站调用 | `http_out` | 本系统 → 外部 HTTP | Feign / RestClient / WebClient 拦截器 |

> 服务间 **内部 Feign**（`mall-*` 互调）默认打精简 `http_out`（可关 body），避免日志爆炸；**真正外部域名 / 第三方** 必须打全量（脱敏后）审计字段。

### 3.2 Topic 规划

| Topic | 内容 | Partition Key 建议 | 保留（起步） |
|---|---|---|---|
| `mall.logs.app` | 运行日志 | `service` 或 `trace_id` | 3～7 天 |
| `mall.logs.http.in` | 入站访问 | `trace_id` 或 `client_ip` | 7～14 天 |
| `mall.logs.http.out` | 出站调用 | `trace_id` 或 `target_host` | 7～14 天 |

也可用单 Topic `mall.logs` + 消息头 / 字段 `log_type` 区分；**推荐分 Topic**，便于：

- 不同保留与磁盘配额  
- 不同 Consumer 订阅（审计组只订 http.in/out）  
- 独立限流与积压治理  

起步可用 `replication.factor=1`（与当前单机 Kafka 一致）；生产至少 `RF=2/3`，`min.insync.replicas=2`。

### 3.3 统一消息信封（Envelope）

所有写入 Kafka 的消息使用统一 JSON，便于多下游解析：

```json
{
  "schema_version": "1.0",
  "log_type": "http_in",
  "timestamp": "2026-07-26T14:30:00.123+08:00",
  "service": "mall-gateway",
  "env": "dev",
  "host": "host-name",
  "trace_id": "....",
  "span_id": "....",
  "level": "INFO",
  "logger": "access",
  "thread": "reactor-http-nio-3",
  "message": "HTTP IN",
  "platform": "mall",
  "payload": { }
}
```

- `payload`：类型相关字段（见第 4 节）。  
- `trace_id` / `span_id`：迁移期可继续用 SkyWalking TID；切 SigNoz 后统一为 **W3C `traceparent` / OTel TraceId**（需网关与 SDK 透传）。

## 4. 字段模型

### 4.1 运行日志 `log_type=app`（payload）

| 字段 | 说明 |
|---|---|
| `mdc` | 可选 MDC 快照（如 `client_ip`） |
| `stack_trace` | ERROR 时堆栈（注意截断，建议 ≤ 16KB） |
| `markers` | 可选业务标记 |

与现有 LogstashEncoder 字段对齐：`platform`、`app_name`、`tid` 等，迁移时做字段映射表即可。

### 4.2 入站访问 `log_type=http_in`（payload）

| 字段 | 必填 | 说明 |
|---|---|---|
| `direction` | 是 | 固定 `IN` |
| `method` | 是 | GET/POST/... |
| `path` | 是 | 规范化 path（不含敏感 query 明文策略见安全节） |
| `query` | 否 | query string（脱敏后） |
| `status` | 是 | HTTP 状态码 |
| `duration_ms` | 是 | 耗时 |
| `client_ip` | 是 | 真实客户端 IP（`x-real-ip` / `x-forwarded-for`） |
| `user_id` | 否 | 登录用户 |
| `request_headers` | 是 | Map，**脱敏后** |
| `request_cookies` | 是 | Map 或原始串解析后，**脱敏后** |
| `request_body` | 条件 | 文本/JSON；二进制/multipart 只记 `content_type` + `size` + `omitted=true` |
| `response_headers` | 否 | 建议采样或仅错误请求全量 |
| `response_body` | 否 | 默认关闭；可对 4xx/5xx 采样开启 |
| `content_type` | 否 | |
| `body_size` | 否 | 原始字节数 |
| `truncated` | 否 | true 表示 body/header 被截断 |

**采集位置建议：**

1. **主路径**：`mall-gateway` GlobalFilter / WebFilter（一处收敛，覆盖所有经网关流量）。  
2. **兜底**：各服务 `OncePerRequestFilter`（直连端口、健康检查旁路除外）。

### 4.3 出站调用 `log_type=http_out`（payload）

| 字段 | 必填 | 说明 |
|---|---|---|
| `direction` | 是 | 固定 `OUT` |
| `target_system` | 建议 | 逻辑名：如 `wechat-pay` / `sms-provider` |
| `method` | 是 | |
| `url` | 是 | 完整 URL（query 脱敏） |
| `host` | 是 | |
| `status` | 是 | 下游状态；超时/网络失败用约定码（如 `-1`） |
| `duration_ms` | 是 | |
| `error` | 否 | 异常类名 + 简讯 |
| `request_headers` | 是 | 脱敏后 |
| `request_cookies` | 否 | 若客户端库携带 Cookie |
| `request_body` | 条件 | 同入站规则 |
| `response_headers` | 建议 | |
| `response_body` | 建议 | 第三方对账场景建议保留（脱敏+截断） |
| `retry_count` | 否 | |

**采集位置建议：**

| 客户端 | 拦截方式 |
|---|---|
| OpenFeign | `RequestInterceptor` + 自定义 `Logger` / `Capability` 记录响应 |
| RestClient / RestTemplate | `ClientHttpRequestInterceptor` |
| WebClient | `ExchangeFilterFunction` |
| JDK HttpClient | 装饰器或统一封装在 `mall-utils` |

统一封装进 **`mall-utils`（如 `mall-web` / 新建 `mall-observability`）**，业务模块禁止各自打散日志格式。

## 5. 安全与合规（强制）

记录 body / cookie / header **不等于明文落盘所有密钥**。大厂默认「可观测 + 默认可审计 + 默认可脱敏」。

### 5.1 默认脱敏字段（示例，可配置）

| 类别 | 示例 Key |
|---|---|
| 认证 | `Authorization`, `token`, `access_token`, `refresh_token`, `satoken`, `Cookie` 中会话票据 |
| 隐私 | `password`, `pwd`, `id_card`, `bank_card`, `mobile`, `phone` |
| 支付 | `cardNo`, `cvv`, `paySign` 等 |

脱敏策略：`***` 或保留前后各 2～4 位。  
Cookie：解析为 kv 后按 key 脱敏，**禁止整段 Cookie 明文**进 ES/SigNoz（除非独立高权限审计仓 + 加密）。

### 5.2 体积与性能护栏

| 项 | 建议默认 |
|---|---|
| body 最大采集 | 8KB～32KB，超出截断并 `truncated=true` |
| header 总长度 | 8KB |
| multipart / 文件上传 | 不采集文件内容 |
| 健康检查、静态资源 | 不打 `http_in` 或采样 1% |
| 成功 GET 出站 | 可采样；失败/超时 **100%** |
| 异步发送 | Kafka appender 必须异步；队列满策略：`drop` + 指标告警（禁止反压堵业务线程） |

### 5.3 访问控制

- ES / SigNoz 按环境隔离（dev/test/prod）。  
- prod 的 `http_in` / `http_out` 索引权限收紧（研发只读脱敏视图，安全/值班可查全量审计索引）。

## 6. 下游接入设计

### 6.1 Elasticsearch（检索主路径，延续现有能力）

```text
Kafka (mall.logs.*) → Logstash kafka input → filter → elasticsearch output
索引建议：
  mall-app-YYYY.MM.dd
  mall-http-in-YYYY.MM.dd
  mall-http-out-YYYY.MM.dd
ILM：与现有 mall-logs-3d / 后续按类型延长 http 审计保留
```

Logstash 侧：

- 关闭自带 ILM（`ilm_enabled => false`），沿用 ES 模板策略。  
- 用 `[log_type]` 路由到不同 index。  
- 过渡期可同时保留 TCP input（阶段 2 前），方便回滚。

### 6.2 SigNoz（替换 SkyWalking）

推荐路径：

```text
Kafka → OpenTelemetry Collector (kafka receiver)
      → OTLP exporter → SigNoz OTel Collector / SigNoz
```

要点：

1. **链路（Trace）**：应用逐步切到 OpenTelemetry Java Agent / Micrometer Tracing + OTLP，替代 SkyWalking Agent。  
2. **日志（Log）**：  
   - 路径 A（推荐）：Kafka JSON → Collector `transform/log` 转 OTLP Logs → SigNoz；  
   - 路径 B：应用直接 OTLP Logs（与「只打 Kafka」目标冲突，仅作特例）。  
3. SigNoz 内用 `trace_id` 关联 Trace 与 Log；`http_in` / `http_out` 可作为结构化属性检索。  
4. 迁移完成前：SkyWalking GRPC 日志与 SigNoz 可短期并存，以 TraceId 映射表或双写 Trace 做对照。

### 6.3 多地方接入的标准答案

> **应用 → Kafka（唯一远程出口）→ N 个 Consumer Group。**

| 接入方 | Consumer Group 示例 | 职责 |
|---|---|---|
| Logstash→ES | `cg-mall-logstash-es` | 全文检索、看板、长期排障 |
| OTel→SigNoz | `cg-mall-otel-signoz` | 链路+日志一体观测 |
| 审计归档（可选） | `cg-mall-audit-archive` | http_in/out 冷存 OSS |
| 实时风控（可选） | `cg-mall-security` | 异常 IP / 爆破检测 |

同一 Topic 多 Group **互不影响 offset**；这是「日志接到多个地方」的正确打开方式。

## 7. 应用侧实现要点（落地时）

### 7.1 运行日志

- 保留 console + 本地 rolling file。  
- 新增 `KafkaAppender`（如 `com.github.danielwegener.logback.kafka.KafkaAppender` 或 logstash-logback 的 Kafka 支持），JSON 与 Envelope 对齐。  
- **阶段 0**：不改现有 `logstash` / `skywalking` appender 引用。  
- **阶段 2**：root 仅保留 `kafka`（+ console/file）；下线 TCP/GRPC。

### 7.2 入站 `http_in`

网关伪代码职责：

1. 包装 request，缓存 body（注意 WebFlux `DataBuffer` 限制与内存）。  
2. 记录开始时间、trace 上下文。  
3. chain 完成后写一条 `http_in`（成功失败都记）。  
4. 脱敏 → 截断 → 异步发 Kafka（或先打结构化 logger，由 KafkaAppender 送出）。

### 7.3 出站 `http_out`

在 `mall-utils` 提供：

- `@OutboundLogged(targetSystem="xxx", captureBody=true)` 或统一 Client 包装。  
- 默认开启：外部 URL；内部 `mall-*` 服务名可配置关闭 body。

### 7.4 与现有注释/代码约束

- 公共能力进 `mall-utils`，禁止在 `mall-demo` 沉淀生产日志组件。  
- 密钥仅环境变量 / Nacos，Kafka 账号密码不入库。

## 8. 分阶段演进路线

| 阶段 | 内容 | 退出标准 |
|---|---|---|
| **P0 现状冻结** | 保持 Logstash TCP + SkyWalking GRPC；本文档评审通过 | 无行为变更 |
| **P1 Kafka 基建** | Topic 创建、权限、监控（lag/盘满）；Logstash 增加 kafka input（旁路消费） | 能从 Kafka 落到 ES 测试索引 |
| **P2 双写运行日志** | 应用增加 KafkaAppender，与 TCP **并行** | Kafka 与 ES 条数抽样误差可接受 |
| **P3 HTTP 审计** | 网关 `http_in` + utils `http_out`；脱敏与截断开关 | Kibana 可查完整脱敏样例 |
| **P4 SigNoz** | 部署 SigNoz + OTel Collector；Trace 试点一服务 | 该服务链路在 SigNoz 可查 |
| **P5 切主** | 运行日志以 Kafka 为主；下线 Logstash TCP；SkyWalking 下线 | 故障演练通过 |
| **P6 收尾** | 仅保留 console/file + Kafka；文档与告警面板定稿 | 无直连 ES/SigNoz 的应用依赖 |

**回滚策略：** 任一阶段保留上一通道开关（logback springProfile / Nacos 开关），5 分钟内可切回 TCP。

## 9. 可观测性与运维

### 9.1 必须监控的指标

- Kafka：`Consumer Lag`（按 Group）、磁盘、ISR。  
- 应用：KafkaAppender 丢弃数、发送失败数、队列深度。  
- Logstash / OTel Collector：消费速率、失败重试、背压。  
- ES / SigNoz：写入拒绝、ILM 删除、磁盘水位。

### 9.2 告警建议

| 条件 | 级别 |
|---|---|
| 任一日志 CG lag > 10 万 且持续 10 分钟 | P2 |
| Appender drop 速率 > 0 持续 5 分钟 | P2 |
| http_out 错误率突增（按 target_system） | P2/P1 |
| Kafka / ES 磁盘 > 80% | P1 |

### 9.3 本地与联调

- IDE 连 Kafka EXTERNAL：`192.168.3.237:9094`（与现 compose 一致）。  
- SOCKS 代理需配置 `NonProxyHosts`，避免再现 TCP/MySQL 超时类问题。

## 10. 方案对比结论

| 方案 | 评价 | 结论 |
|---|---|---|
| 继续叠加 Appender（ES+SW+SigNoz） | 短期快，长期不可维护 | 否 |
| 仅 Filebeat 扫本地日志 | 无出入站结构化审计，多机运维重 | 仅作兜底 |
| **Kafka 总线 + 多 Consumer** | 解耦、削峰、易扩展到 SigNoz/ES/审计 | **采纳** |
| 应用直连 OTLP 到 SigNoz + 另连 ES | 仍是双出口 | 仅过渡可接受 |

**架构定稿一句话：**  
应用只向 Kafka 输出「运行日志 + 入站审计 + 出站审计」三类结构化事件；Elasticsearch 负责检索，SigNoz 负责链路与关联日志；敏感字段默认脱敏，体积默认截断。
