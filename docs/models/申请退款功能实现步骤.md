# 申请退款功能实现步骤

> 对齐文档：《商城系统设计方案》§3.2.6 售后（简化版）、§3.3.2 商家售后管理  
> 现状：前端「我的订单」详情抽屉已有「申请退款」按钮（无点击逻辑）；后端无退款表/接口；支付为余额假支付（`oms/pay` + `ExtendSysUserService.deduct/recharge`）。

## 一、本期范围（V1.0 简化版）

| 项 | 约定 |
|---|---|
| 退款类型 | **仅退款**（不退货、不换货） |
| 可申请条件 | 订单已支付且**未发货**：`order_status = 1`（待发货） |
| 流程 | 用户提交申请 → 商家/管理员审核 → 通过则退回余额 + 回补库存 → 订单置为已退款 |
| 支付渠道 | 仅余额（与现有假支付一致）；真实微信/支付宝退款二期 |
| 不做 | 部分退款、已发货退款、退货物流、批量审核、对账 |

**前端按钮纠偏**：当前 `orderStatus === 1/2/3` 都展示「申请退款」；V1 应收窄为 **仅 `order_status === 1`**。状态 2/3 留给二期「退货退款」。

## 二、状态与流程

### 2.1 订单状态扩展

现有：`0待付款 / 1待发货 / 2已发货 / 3待收货 / 4已完成 / 5已关闭 / 6无效`

建议新增（或复用注释中的扩展位，落库需改 COMMENT）：

| 值 | 含义 | 说明 |
|---|---|---|
| 7 | 退款中 | 用户已申请，待审核 |
| 8 | 已退款 | 审核通过且余额已退 |

流转：

```
待发货(1) ──申请退款──► 退款中(7) ──审核通过──► 已退款(8)
                         │
                         └──审核拒绝──► 待发货(1)（恢复可发货）
```

### 2.2 退款单状态

| 值 | 含义 |
|---|---|
| 0 | 待审核 |
| 1 | 已通过 |
| 2 | 已拒绝 |
| 3 | 已取消（用户撤销，可选） |

## 三、数据模型

### 3.1 新建表 `oms_order_refund`（退款申请单）

职责：一笔订单一次有效退款申请（V1 整单仅退款）；支撑用户查询、商家审核列表。

建议字段（含基础字段）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 主键 |
| refund_no | varchar(32) | 退款单号（流水号服务生成） |
| order_id | bigint | 订单 id |
| order_code | varchar(64) | 订单编号（冗余查询） |
| user_id | bigint | 申请人 |
| business_org_id | bigint | 商家组织（对齐 oms_order） |
| refund_amount | decimal(12,2) | 退款金额（= 订单 pay_amount） |
| reason_type | int | 原因类型（字典，可选） |
| reason | varchar(500) | 退款说明 |
| refund_status | int | 0待审核/1通过/2拒绝/3取消 |
| audit_user_id | bigint | 审核人 |
| audit_time | datetime | 审核时间 |
| audit_remark | varchar(500) | 审核备注 |
| create_time / update_time / invalid | | 基础字段 |

索引建议：

- `uk_refund_no`：`refund_no`
- `idx_order_id`：`order_id`（同一订单有效申请唯一可用业务约束：待审核/已通过仅允许一条）
- `idx_status_time`：`(refund_status, create_time)`（审核列表）
- `idx_user_id`：`user_id`

> DDL 实现时按 `design-mysql-table` 规范输出完整 `CREATE TABLE`，脚本建议落 `docs/sql/`。

### 3.2 订单表（可选改动）

- 更新 `order_status` COMMENT，增加 7/8
- **不必**在订单表堆退款明细字段；以退款单为准

## 四、后端实现步骤（mall-oms）

### Step 1：枚举与常量

1. `OmsOrderStatusEnum` 增加 `REFUNDING(7)`、`REFUNDED(8)`
2. 新增 `OmsRefundStatusEnum`
3. 权限码建议：
   - 用户：`api:oms:refund:apply`、`api:oms:refund:mine`
   - 管理：`api:oms:refund:page`、`api:oms:refund:audit`

### Step 2：DAO 层

1. Entity / Mapper：`OmsOrderRefund`
2. DTO：`OmsRefundApplyDto`（orderId、reason、reasonType）
3. DTO：`OmsRefundAuditDto`（refundId、pass、auditRemark）
4. QueryDto + VO：列表/详情展示

### Step 3：领域服务 `OmsOrderRefundService`

**申请 `apply`：**

1. 校验登录用户 = 订单 `user_id`
2. 校验 `order_status == 1` 且已支付（`pay_type != 0` 或 `pay_time != null`）
3. 校验无进行中的退款单（`refund_status = 0`）
4. 写退款单；订单状态 → `7`
5. 事务：订单更新 + 退款单插入

**审核 `audit`：**

1. 校验退款单待审核、订单为退款中
2. **拒绝**：退款单 → 2；订单 → `1`；记审核人/备注
3. **通过**：
   - `ExtendSysUserService.recharge(userId, refundAmount)` 退余额
   - 按订单商品回补库存（`ExtendPmsStockService` 增加/复用入库能力；当前下单直接扣减，回补用 `add`/`addBatch`）
   - 退款单 → 1；订单 → `8`
4. 全程事务；余额与库存失败则整单回滚

**查询：**

- 用户：我的退款单分页 / 按订单查最新退款单
- 管理：待审核分页、详情

### Step 4：Controller

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/oms/order/mine/refund/apply` | 用户申请 |
| POST | `/oms/order/mine/refund/page` | 用户退款列表（可选） |
| POST | `/oms/order/mgr/refund/page` | 管理端审核列表 |
| POST | `/oms/order/mgr/refund/audit` | 审核通过/拒绝 |
| POST | `/oms/order/refund/get` | 详情（可选，按 refundId/orderId） |

复用现有分层：`mall-oms-dao` → `mall-oms-core` → `mall-oms-startup`；跨服务仅用已有 Feign（sys 余额、pms 库存）。

### Step 5：幂等与安全

- 申请：同一订单存在待审核单则拒绝重复申请
- 审核：仅 `refund_status=0` 可审；乐观锁或 `update ... where status=0`
- 金额以后端订单 `pay_amount` 为准，禁止前端传入退款金额
- `@SaCheckPermission` + 用户只能操作自己的订单

## 五、前端实现步骤（yz-mall-web-admin-pc）

### Step 1：API

在 `src/api/oms.ts` 增加：

- `omsRefundApply`
- `omsRefundMinePage`（可选）
- `omsRefundMgrPage`
- `omsRefundAudit`

### Step 2：我的订单详情

文件：`src/views/mall/order/mine/utils/hook.tsx`

1. 「申请退款」仅在 `orderStatus === 1` 显示
2. 点击弹出对话框：退款原因（必填）、说明
3. 提交成功：提示 → 关闭抽屉 → 刷新列表 → 重新打开详情（状态应为退款中）
4. `orderStatus === 7`：展示「退款审核中」，隐藏申请按钮
5. `orderStatus === 8`：展示「已退款」

### Step 3：订单管理端售后

1. 新增菜单「售后管理」或在 `mall/order/manger` 增加 Tab「退款审核」
2. 列表：待审核/已处理；操作：通过、拒绝（拒绝需填备注）
3. 详情展示订单号、金额、原因、申请人

### Step 4：状态文案

订单列表/详情中 `orderStatus` 增加 7、8 的中文与 Tag 颜色。

## 六、推荐落地顺序（执行清单）

```text
[ ] 1. 定稿状态枚举与可申请条件（仅待发货）
[ ] 2. 输出 oms_order_refund DDL + 执行（docs/sql）
[ ] 3. OMS：Entity/Mapper/DTO/枚举
[ ] 4. OMS：apply + 单测/手工接口验证
[ ] 5. OMS：audit（退余额 + 回库存）+ 手工验证
[ ] 6. OMS：管理端分页查询
[ ] 7. 前端：申请弹窗 + 按钮条件修正
[ ] 8. 前端：管理端审核页
[ ] 9. 联调：下单→支付→申请→拒绝→再申请→通过→查余额与库存
[ ] 10. 菜单/权限码入库（sys_menu / 角色授权）
```

## 七、验收标准

1. 待付款/已发货订单不能申请；待发货可申请
2. 申请后订单为「退款中」，管理端可见待审单
3. 拒绝后订单回到「待发货」，可再次申请或正常发货
4. 通过后：用户余额增加 `pay_amount`；对应 SKU 库存回补；订单「已退款」；不可重复申请
5. 重复申请、重复审核均有明确业务错误提示

## 八、风险与后续

| 风险 | 处理 |
|---|---|
| 下单已扣库存、无锁定模型 | 退款通过时按订单行 `productId/skuId + quantity` 回补；与后续「锁定库存」改造兼容 |
| 余额退款非真实支付渠道 | V1 只调 `recharge`；二期按 `pay_type` 走渠道退款 |
| 前端按钮范围过宽 | 先改展示条件，避免已发货误申请 |

二期：已发货退货退款、部分退款、物流回寄、独立 `mall-pay` 退款流水表。
