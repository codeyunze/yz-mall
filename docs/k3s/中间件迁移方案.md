# docker-compose 中间件迁移到 k3s 方案

源文件：[`docs/docker/docker-compose.yml`](../docker/docker-compose.yml)（路径是 **docs**，不是 dcs）。

目标环境：单节点 k3s（当前约 **3.6Gi 内存 / 59G 盘**，已运行 RustFS + Dashboard 等）。

## 1. 结论先说

**不能也不应一次性把 compose 里全部服务搬进现有这台 k3s。**  
compose 仅 ES+Kibana 就声明约 3Gi 内存上限，再加上 Nacos、RocketMQ、Kafka、Prometheus 等，远超当前节点可用内存。

建议：

1. **按业务优先级分批迁移**  
2. **升配节点或拆多节点** 后再迁重型组件（ES/Kibana/Kafka 等）  
3. MySQL **不在** 本 compose 内（xxl-job / mysqld-exporter 依赖外部 MySQL），迁移时仍指向现有库，勿默认把库也塞进 k3s

## 3. 当前节点资源约束（硬限制）

| 资源 | 现状 | 含义 |
|---|---|---|
| 内存 | 约 3.6Gi，可用约 2.4Gi | 塞不下 ES+Kibana+全套 MQ/Kafka |
| 磁盘 | 约 59G，已用约 17% | 短期够，ES/Kafka 数据需规划 PVC |
| 已占用 | RustFS、Traefik、Dashboard 等 | 再迁必须设 `resources.requests/limits` |

**在现节点上可考虑的首批（示例）**：Redis + Nacos（均限制内存、外置或轻量存储）。  
**不建议同机再上**：Elasticsearch、Kibana、Kafka 全量、再加一套 Prometheus（除非升配到 ≥8Gi，且 Dashboard 改端口）。

## 4. 迁移原则（对齐 yz-mall / k3s）

1. **镜像继续走 ACR** `registry.cn-guangzhou.aliyuncs.com/devyunze/...`，避免 Docker Hub。  
2. **一服务一命名空间或统一 `mall-middleware` + 标签区分**（建议统一 `mall-middleware`，Dashboard 好筛）。  
3. 配置进 **ConfigMap**，密钥进 **Secret**；compose 里的明文密码迁移时轮换。  
4. 数据目录 → **PVC + local-path**（已验证 helper 需 ACR busybox）。  
5. 服务发现用 **K8s Service DNS**（如 `redis.mall-middleware.svc.cluster.local:6379`），应用侧改 Nacos/配置中心地址。  
6. 对外入口：内网用 `LoadBalancer/NodePort`，公网谨慎；与 Traefik Ingress 按需结合。  
7. **端口冲突预先规划**（尤其 9090：Dashboard vs Prometheus）。  
8. 有状态服务先 **双跑验证**，再切流量、再停 compose。

## 5. 推荐分批计划

### P0 — 应用启动最小集（优先）

- Redis  
- Nacos（配置/注册；MySQL 仍用现有库）

交付物：`Deployment/StatefulSet + Service + ConfigMap/Secret + PVC(可选)`，文档记录连接串变更。

### P1 — 消息与任务

- RocketMQ（namesrv + broker + 可选 dashboard）  
- XXL-JOB Admin  
- Seata（若业务仍用）

注意：RocketMQ / Seata 里所有 **写死 IP** 改为 Service 名或向下注入的 Pod IP 策略。

### P2 — 日志检索与流式

- Kafka + kafka-ui  
- 或先保留 compose 上的 Kafka，k3s 只跑业务  

### P3 — ELK + 可观测性

- ES + Kibana + Logstash  
- Prometheus + Grafana + exporters  

前提：**升配** 或 **独立监控/日志节点**；Prometheus 避开 9090 或给 Dashboard 换端口。

## 6. 目录建议（落地时）

```text
yz-mall/docs/k3s/middleware/
  README.md                 # 总览与切换清单
  redis/
  nacos/
  rocketmq/
  kafka/
  elk/
  monitoring/
  values/ 或 overlays/      # 环境差异
```

也可用 Helm Chart / Kustomize；与现有 RustFS「Helm + ACR」方式保持一致即可。

## 7. 切换与回滚

1. k3s 部署并 `curl`/业务探活通过  
2. 改应用配置（Nacos、直连地址）指向新 Service  
3. 观察一段时间  
4. `docker compose stop` 对应服务（勿先删卷）  
5. 回滚：改回 compose 地址即可  

## 8. 需要你确认的事项

请直接回复优先级，例如：

1. **首批迁哪些？**（建议：`redis + nacos`）  
2. **是否升配这台机，还是另备节点？**（不升配则不做 ES/Kafka）  
3. **Prometheus 与 Dashboard 的 9090**：Dashboard 改端口，还是 Prometheus 用别的端口？  
4. **MySQL / Nacos 数据库** 是否继续用现有实例（推荐继续）？  

确认后从 P0 开始写清单并在 k3s 上部署。
